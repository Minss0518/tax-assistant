# 국가법령정보 API 연동 — 종합소득세 데이터 파이프라인 설계

- 상태: 승인됨 (구현 대기)
- 관련 기존 코드: `backend/app/services/rag_service.py:127`(`get_or_create_index`),
  `backend/app/tax_agent/nodes/retrieve.py`(LangGraph 에이전트의 검색 노드)

## 배경 / 목표

기존 세무비서는 소득세법 PDF를 수동 다운로드해서 임베딩한 정적 데이터에 의존한다.
이 작업은 법제처 "국가법령정보 공동활용" Open API(open.law.go.kr)를 연동해서,
**종합소득세 관련 법령/판례/법령해석례를 API로 가져와 최신 상태로 인덱싱**하는
배치 파이프라인을 구축하는 것이다.

RAG 검색 자체(LlamaIndex + ChromaDB)는 그대로 두고, **그 벡터DB에 들어가는 데이터의
출처를 "정적 PDF"에 더해 "API 자동 수집"으로 추가**하는 것이 이번 작업의 스코프다.
기존 PDF 컬렉션은 유지하고, API 수집 데이터는 별도 컬렉션으로 분리한다.

## 확인된 API 정보 (law만 실제 테스트 완료)

- Base URL: `https://www.law.go.kr/DRF/`
- 인증: `OC=<발급받은 인증키>` 쿼리 파라미터
- **목록조회**: `lawSearch.do?OC={OC}&target={target}&type=JSON&query={검색어}`
  - `target=law` : 현재 법령 검색
  - `target=prec` : 판례 검색
  - `target=expc` : 법령해석례 검색
  - 응답에서 각 항목의 `법령ID`, `법령상세링크`(안에 `MST=` 값 포함) 확인 가능
  - **페이지네이션 필수 처리**: "종합소득세" 키워드로 prec/expc 검색 시 결과가 수십~수백
    건일 수 있음. `display`(페이지당 건수), `page` 파라미터로 전체 페이지를 순회하며
    수집하고, `totalCnt` 필드로 종료 조건을 판단한다. 1페이지만 가져오고 끝내지 않는다.
- **본문조회 — law**: `lawService.do?OC={OC}&target=law&MST={MST값}&type=JSON`
  - 응답 최상위: `법령` → `개정문`(불필요, 스킵), `기본정보`, `조문`
  - `조문` 안에 `조문단위` 배열, 각 원소가 `조문번호`, `조문제목`, `조문내용`을 가짐
  - `조문내용`이 실제 인덱싱 대상 텍스트
  - 실제 확인된 값: 소득세법 검색 시 `법령ID=001565`, `MST=280405`. MST는 개정 시 바뀔
    수 있으므로 **하드코딩하지 않고 항상 검색 단계를 먼저 거쳐 최신값을 확인**한다.
- **본문조회 — prec / expc: 스키마 미확인, 구현 1단계에서 반드시 별도 검증**
  - law와 동일한 구조라고 가정하지 않는다. 판례는 `판시사항`/`판결요지`/`전문` 계열,
    법령해석례는 `해석례본문` 계열 필드로 올 것으로 예상되나, law를 검증한 것과 동일하게
    실제 응답을 호출해서 확인한 뒤 파서를 설계한다.

## 응답 정제 (모든 target 공통)

API 응답의 텍스트 필드(조문내용, 판시사항 등)에는 HTML 태그, 전각공백, 연속 공백 등이
섞여 있을 수 있다. 임베딩 전에 정제 단계(태그 제거, 공백 정규화)를 거친다. 정제 함수는
target별 파서에서 공통으로 재사용할 수 있게 별도 유틸(`clean_text.py`)로 분리한다.

## 파이프라인 단계

### [1] 검색 (search)

- `target=law`로 `query=소득세법` 검색 → 소득세법 본법의 최신 MST 확보
- 하위법령(시행령/시행규칙)은 1차 스코프에서는 제외, 본법만으로 시작
- `target=expc`, `target=prec`로 `query=종합소득세` 검색 → 관련 법령해석례/판례 MST 확보
  (페이지네이션 전체 순회)

### [2] 본문 조회 (fetch)

- [1]에서 얻은 각 MST로 `lawService.do` 호출해 본문을 JSON으로 받음
- **target별 별도 파서**: `parse_law_response()`, `parse_prec_response()`,
  `parse_expc_response()`를 각각 구현한다. law 이외의 실제 응답 구조는 구현 1단계에서
  최초 1회 호출로 확인한 뒤 코드에 반영한다.
- API 호출 실패/타임아웃에 대비해 재시도 로직(3회, 지수 백오프) 포함
- **호출 빈도 제한 고려**: 여러 조문/판례를 순차 또는 병렬로 호출할 때 요청 사이 짧은
  슬립(0.1~0.2초) 또는 세마포어로 동시 호출 수를 제한한다. 429 등 제한 응답 발생 시
  백오프를 늘린다.

### [3] 필터링 (종합소득세 관련 조문만 추출)

- 소득세법은 이자·배당·사업·근로·연금·기타소득, 종합소득, 퇴직소득, 양도소득 등을 모두
  포괄하므로, 전체 조문 중 아래 기준으로 필터링한다:
  - 조문제목 또는 조문내용에 "종합소득"이 포함된 조문
  - 소득세법의 장(章) 구조상 종합소득 관련 장에 속하는 조문번호 범위 (실제 API 응답에
    편장절 구분 필드가 있는지 구현 시점에 먼저 확인해서 반영)
- 법령해석례/판례는 검색 단계에서 이미 "종합소득세" 키워드로 좁혀져 있으므로 별도 필터링
  불필요 (검색된 결과 전체를 사용)
- **알려진 한계**: 이 필터는 "종합소득"이라는 단어가 직접 언급된 조문만 잡는다. 종합소득세
  계산에 실제로 쓰이지만 다른 장에 있고 "종합소득"이라는 단어를 안 쓰는 공제 관련 조문
  (예: 인적공제 등)은 필터에서 누락될 수 있다. 검색 결과 품질을 보고 필터 기준을 조정할
  여지를 남겨둔다.

### [4] 청크 분할 및 메타데이터 부착

- **law**: 조문 단위(조문번호 기준)로 1개 청크 = 1개 조문. 조문이 과도하게 길면 항/호
  단위로 추가 분할 고려
- **prec / expc**: [2]에서 확인한 실제 필드 구조에 맞춰 청크 단위를 별도로 정한다
  (예: 판시사항+판결요지를 하나로, 전문은 별도 청크 등 — 구현 시점에 확인 후 결정)
- **메타데이터 키는 기존 코드와 반드시 통일한다.** `retrieve.py:26`이
  `n.node.metadata.get("file_name", "unknown")`로 PDF 리더가 자동 채운 `file_name` 키를
  기대하고 있다. 새 API 데이터도 `file_name` 키에 사람이 읽을 출처 문자열(예:
  `"소득세법 제14조"`, `"대법원 2023두12345"`)을 넣어 기존 코드와 100% 호환시킨다
  (`retrieve.py` 수정 불필요).
  - 추가 메타데이터(`조문번호`, `시행일자`, `데이터유형`, `수집일시`)는 `file_name`과
    별개로 계속 부착 — 향후 verify_node 개선 시 활용 가능하도록 남겨둔다. 단, 이번
    스코프에서 verify_node 자체를 고치지는 않는다 (아래 "스코프 밖" 참고).

### [5] 임베딩 및 인덱싱

- 기존 세무비서가 쓰던 임베딩 모델 설정을 그대로 재사용
- **컬렉션은 기존 PDF 컬렉션(`tax_documents_v2`)과 별도로 분리한다.** 이유: 데이터 출처가
  다르면 문제 발생 시 원인 추적이 쉽고, 추후 PDF 방식을 걷어낼 때 영향 범위가 명확해진다.
- **재실행 전략: 컬렉션 전체 삭제 후 재구축.** `run_pipeline.py`를 실행할 때마다 API 소스
  전용 컬렉션(예: `tax_law_api_v1`)을 통째로 지우고 [1]~[4]에서 새로 수집한 데이터로
  처음부터 다시 만든다. upsert 방식(조문번호 기준 stable ID)보다 구현이 단순하고, 개정
  전/후 조문이 동시에 검색되는 문제를 원천 차단한다. 단점(매번 전체 재수집·재임베딩
  비용)은 법령 개정이 잦지 않다는 점, 그리고 [6]에서 이번 스코프는 수동 실행이라는 점을
  고려하면 감내 가능한 수준으로 판단.
- **컬렉션 분리에 따라 반드시 같이 수정해야 하는 소비처 2곳 (이번 스코프에 포함):**
  1. `backend/app/services/rag_service.py:127` — `get_or_create_index()`가 컬렉션명
     `"tax_documents_v2"`를 하드코딩. 이 함수를 호출하는 `rag_service.py:150`(기존
     `/chat`)과 `tax_agent/nodes/retrieve.py:12`(LangGraph 에이전트) 두 곳 모두, 기존
     PDF 컬렉션과 신규 API 컬렉션을 **각각 검색해서 결과를 합치는 방식**으로 수정한다.
  2. 두 소비처의 병합 로직(유사도 점수 기준 정렬 등)을 통일해서 한쪽만 고치고 다른 쪽을
     빠뜨리는 일이 없게 한다. 두 컬렉션에서 각각 top-k를 가져온 뒤 점수 기준으로 재정렬해
     상위 N개만 최종 사용하는 방식을 기본으로 한다 (정확한 top-k 값은 구현 시점에 결정 —
     기존 `similarity_top_k=5`와 균형을 고려해 결과가 과도하게 늘어나 프롬프트 크기를
     키우지 않도록 주의).

### [6] 배치 갱신 스케줄 (선택 사항, 1차 스코프 밖)

법령은 자주 바뀌지 않으므로 매일 돌릴 필요는 없음. 수동 실행 스크립트로 먼저 구현하고,
추후 필요시 주기적 실행(cron 등)으로 확장.

## 설정 / 이용약관

- `OC` 인증키는 코드에 하드코딩하지 않는다. 기존 `app/config.py`의 `Settings` 클래스에
  `OPENAI_API_KEY`와 같은 방식으로 `LAW_API_OC` 필드를 추가하고, `.env`에서 읽어온다.
- 국가법령정보 Open API의 상업적 이용 가능 여부, 출처표시 의무 등 이용약관을
  open.law.go.kr 마이페이지/이용안내 페이지에서 배포 전에 확인해둔다 (코드 작업은 아님).

## 파일 구조

프로젝트 임포트 경로 문제를 피하기 위해 LangGraph 작업 때와 동일하게 `backend/` 하위에
둔다 (`chunk_and_index.py`가 `rag_service.py`의 `init_llama_settings()`, `CHROMA_PATH`
등을 재사용하려면 `app.*` 임포트가 필요).

```
backend/
├── app/
│   └── config.py            # LAW_API_OC 필드 추가 (기존 파일 수정)
├── tax_law_pipeline/
│   ├── law_api_client.py     # lawSearch.do / lawService.do 호출 래퍼 (target별 파서, 재시도/rate limit 포함)
│   ├── clean_text.py          # HTML 태그/공백 정제 유틸 (target 공통)
│   ├── filter_articles.py     # 종합소득 관련 조문 필터링 로직 (law 전용)
│   ├── chunk_and_index.py     # 청크 분할, 메타데이터 부착(file_name 키 호환), 컬렉션 삭제 후 재구축, 임베딩/인덱싱
│   └── run_pipeline.py        # 위 단계를 순서대로 실행하는 진입점 스크립트
└── tests/
    └── tax_law_pipeline/
        └── test_filter_articles.py  # 필터링 로직 단위 테스트 (실제 API 응답 샘플로 검증)
```

(`backend/tests/`는 `pytest.ini`의 `testpaths = tests`로 이미 자동 수집되므로, 새 테스트도
이 하위에 위치시킨다.)

## 구현 우선순위

0. `app/config.py`에 `LAW_API_OC` 환경변수 필드 추가
1. `law_api_client.py`로 law/prec/expc **세 target 모두** 실제 호출해서 응답 구조를 확인
   (law는 이미 확인 완료, prec/expc는 필수로 이번에 확인)
2. 확인된 구조를 바탕으로 target별 파서 3종 + `clean_text.py` 구현
3. `filter_articles.py` — 종합소득 관련 조문 추출 (law의 편장절 구분 필드 존재 여부 확인
   후 설계)
4. **컬렉션 분리 결정에 따라 `rag_service.py:127`, `retrieve.py:12` 두 곳을 함께 수정**
   (병렬 검색 + 결과 병합 로직). 이 단계를 빠뜨리면 새 데이터가 검색에 전혀 반영되지 않음
5. `chunk_and_index.py` — 메타데이터를 `file_name` 키와 호환되게 부착, 실행 시마다 API
   소스 컬렉션 삭제 후 재구축
6. `run_pipeline.py`로 전체 통합, 실제 ChromaDB에 반영 후 세무비서로 질의 테스트

## 이번 스코프 밖 — 후속 작업으로 명시

- `verify_node`(`backend/app/tax_agent/nodes/verify.py`)는 현재 `retrieved_docs`의
  content만 사용하고 메타데이터(시행일자, 데이터유형 등)를 검증에 활용하지 않는다. 이번
  파이프라인으로 메타데이터를 채워도 verify_node가 그것을 쓰도록 고치지 않으면 실질적인
  검증 강화 효과는 없다. 다음 작업 후보로 남겨둔다.
- 주기적 자동 실행(cron 등)은 이번 스코프 밖. 수동 실행 스크립트까지만.
- 하위법령(시행령/시행규칙) 수집은 이번 스코프 밖. 본법만.

## 참고 — 왜 이렇게 설계했는지 (면접/문서화용 메모)

- MST를 하드코딩하지 않는 이유: 법령이 개정되면 MST가 바뀔 수 있어, 항상 검색 단계를
  먼저 거쳐 최신값을 확인하게 했다.
- 필터링을 조문제목/장절 기준으로 하는 이유: 소득세법 전체를 다 넣으면 양도소득세,
  퇴직소득세 등 무관한 내용이 검색 노이즈로 섞여 검색 정확도가 오히려 떨어질 수 있다.
- 기존 PDF 컬렉션과 분리하는 이유: 데이터 출처가 다르면 문제 발생 시 원인 추적이 쉬워지고,
  추후 PDF 방식을 완전히 걷어낼 때도 영향 범위가 명확해진다.
- law/prec/expc를 target별로 분리 처리하는 이유: 세 API가 서로 다른 응답 스키마를
  가지므로, 하나의 파서로 억지로 통합하면 필드 누락이나 조용한 파싱 실패가 발생할 위험이
  있다. 각 target의 실제 구조를 확인하고 전용 파서를 두는 것이 더 견고하다.
- 메타데이터 키를 기존 `file_name`과 통일한 이유: 새 데이터 소스를 추가할 때 기존 소비
  코드(`retrieve.py`)를 건드리지 않고도 호환되게 하는 것이, 코드 변경 범위를 최소화하고
  회귀 위험을 줄이는 방법이라고 판단했다.
- 재실행 시 upsert 대신 전체 삭제 후 재구축을 택한 이유: 조문번호 기준 stable ID로
  upsert하는 방식은 ChromaDB API 지원 여부 확인과 ID 설계가 추가로 필요해 구현 복잡도가
  올라간다. 법령 개정이 자주 일어나지 않고 이번 스코프가 수동 실행이라는 점을 고려하면,
  매번 전체 재구축하는 단순한 방식으로 "개정 전/후 조문 공존" 문제를 확실하게 없애는 것이
  더 나은 트레이드오프라고 판단했다.
